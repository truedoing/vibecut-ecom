# 短剧工作台 · 技术决策记录

> 起建 2026-11-13。只记「为什么这么选」，不记功能清单。
> 每条写：背景 → 决定 → 代价。被推翻的判断保留原文并标注取代原因。
> 服务三块：**生成**（接手的人不踩同一个坑）、**教学**（决策过程本身就是课）、
> **自媒体**（可拆成独立故事，见 `docs/UI_教学与自媒体素材.md`）。

## 一、总原则

1. **页面只画不算。** 谁该重做、下一步做什么，由 `status_overview.py` 算；UI 不另写一套判断。
2. **文件是唯一真源。** 状态在 `runs/<剧>/<任务>/状态.json`，当前选中在 `runs/工作台.json`；UI 不落任何状态。
3. **先补数据落盘，再画界面。** 进度先能被机器读到，页面才有东西可画；否则做出来的是静态报告页。
4. **零依赖、本机、只读。** Python 标准库 + 单文件 HTML；不为看板引入框架，不在页面上执行任务。
5. **3 部剧时就要用 30 部的眼光设计。** 当前样本量会骗人，布局和筛选按 30 部考虑。

## 二、决策清单

### D1 页面只画不算

**背景**：状态文件里已经有 `rev / state / depends_rev`，`status_overview.py` 已经能算出 stale 和下一步。
如果网页再写一套「怎么算完成」，两套判断迟早对不上。

**决定**：`status_overview.py --json` 是唯一算法入口，`server.py` 只做数据整形，`index.html` 只做渲染。
页面上的数字全部来自文件，不来自前端推算。

**代价**：想在页面上直接改状态、点「通过」做不到；这些动作回对话或脚本里做。
这是有意的：装配和发布是花钱且不可逆的动作，越权比不方便更贵。

### D2 用 `http.server`，不上 FastAPI

**背景**：一个人、一台机、本机打开，负载是几十个 JSON 和几个视频文件。
这台机器上四个 Python web 框架一个都没装（电商线的 FastAPI 已删）。

**决定**：`skills/short-drama-supervisor/ui/server.py`，标准库 `ThreadingHTTPServer`，单文件启动。

**代价**：路由、Range、JSON 序列化都手写；没有 OpenAPI、没有中间件生态。
到多人协作、需要鉴权或写接口时，应重新评估，而不是继续往上堆。

### D3 只读：只处理 GET

**背景**：工作台的职责是「看进度、看成片」，不是「操作系统」。

**决定**：POST / PUT / DELETE / PATCH 一律 405，并在响应里说「只读页面，要跑任务回对话里说」。
不启动任何脚本、不写任何数据文件、不改状态。

**代价**：所有操作都要切回对话；页面不能当控制台。换来的是：误点不会出片、不会改台账。

### D4 剧列表只读素材根的一级文件夹

**背景**：一开始扫 `assets/short-drama/`，结果混进 `ai_assets`，还把同一部剧的两个名字
（`八零憨妻` / `八零憨妻的甜蜜日常`）算成两条管线。

**决定**：只读 `.env` 的 `SHORT_DRAMA_ASSET_ROOT` 下一级文件夹；剧名对照用 `runs/工作台.json → dramas`。

**代价**：原视频不在这台机器上的历史剧（如八零憨妻）不进管线，只在页面下方单独注明
「片子记录和成片仍在」。这是事实，不硬塞。

### D5 进度口径：素材按份数，分母用已动工集数

**背景**：一部剧有 60 集，实际只分析了 19 集。用 60 当分母，做完的活会显示成 29%；
用「三样都齐的集数」当分子，父爱跨越山海 18 集台词全齐、只差合表会显示 0%。

**决定**：
- 分子：每集要交三份资料（台词 / 镜头标注 / 合表），**按份数**算。
- 分母：**已动工集数** × 3，不换成全剧总集数。
- 全剧集数写进展开细节，把事实摆出来。

**代价**：页面上的 93% 是「已动工范围内」的完成度，不是「全剧」完成度。
必须配合展开里的「全剧 60 集」一起读。

### D6 后两段给数，不给勾

**背景**：《以真心守护至亲》一部剧底下挂着 19 条片子，后两段不是「一个开关」，
是一批片子各自停在不同地方（3 条等人过目 / 12 条通过 / 2 条待拼）。

**决定**：素材分析给集级进度条；文案和出片给「已点头 / 等审 / 要改 / 待拼 / 要重拼」的数，
点开看片子名。不把一部剧压成一个「完成」勾。

**代价**：总览不能一眼回答「这部剧做完了吗」；要配合数字和颜色读。

### D7 先有进度落盘，再有进度页

**背景**：11-12 一次打标进程在 20:15 静默死掉，48 分钟没人发现。根子是脚本只把
「ep15 已打标 24/45 帧」打印到屏幕，屏幕上的东西没人读得到。

**决定**：新增 `progress.py`：**一个任务一个文件**（8 路并发不互相覆盖）、原子写（`.tmp` + `os.replace`）、
带 pid 和更新时间。网页自己判「标着在跑、但进程查不到或三分钟没动静」＝疑似中断。

**代价**：`runs/进度/` 会积累文件；目前没有自动清理。进度上报失败一律静默，绝不能把主线任务搞挂。

### D8 按 (路径, mtime, 大小) 缓存解析结果

**背景**：总览要读 110 个 JSON（共 0.7 MB），接口要 9.7 秒。实测 `os.stat` 110 个只要 1 毫秒，
但**打开一个文件要 60 毫秒**——慢在磁盘，不在 Python。

**决定**：`jload()` 按 `(路径, mtime_ns, size)` 缓存；文件一改 mtime 就变，下次自动重读。
服务启动时后台线程预热。9.7 秒 → 0.8 秒。

**代价**：极端情况下「同路径、同 mtime、同大小」但内容变了，缓存会读到旧值。
在本项目的写盘方式（原子替换、mtime 更新）下可接受。

### D9 当前成片认 `trailer.path`，不认文件名

**背景**：旧逻辑只认 `sd_*.mp4`。但 D1 的成片是 `build/v1.mp4`、D2 是 `build/v2.mp4`，
文件名不带 `sd_`——页面会把真正给人看的成片当成「装配中间文件」。

**决定**：当前成片 = `状态.json → artifacts.trailer.path` 指向的那个文件；
其余按 `vN` / `sd_` / `build/` 分「旧版 / 装配中间文件 / AI 素材段」。
找不到时明确写「状态说已出片，但记的成片不在本机（文件名）」。

**代价**：状态文件写错路径时，页面会如实报「不在本机」，不会替人猜。修状态是人的事。

### D10 时长读 MP4 盒头，不跑 ffprobe

**背景**：预览页要列几十个 mp4。实测这台机上一个 65 MB 的文件跑 ffprobe 要 **5 秒**（磁盘慢），
38 个文件预热要几分钟。

**决定**：自己跳读 `moov/mvhd` + `tkhd`，几十字节拿到时长、宽高；按 (路径, mtime, size) 缓存。

**代价**：只覆盖标准 MP4；异常文件退回「无时长」。不解析音频参数、关键帧、码率——
那些等分镜台真需要时再说，不在看板上做全量探测。

### D11 视频走 Range，206 分段

**背景**：浏览器拖进度条会发 `Range` 请求；整文件读进内存既慢又不能边下边播。

**决定**：`/video/` 支持 `Range: bytes=...`，返回 206 + `Content-Range`；非法范围返回 416。

**代价**：自己处理 seek 和断连（拖进度条、关页面都会断），必须吞掉 `BrokenPipe/ConnectionReset`。

### D12 分镜台延后，先把「看成片」做好

**背景**：张老师要的是「文案与出片之间的预览分镜台」——左镜头清单 / 中竖屏预览 / 右属性 / 底部时间线。
但它需要播原片、按原片时间轴对齐、标切点，工作量远大于看板。

**决定**：先把预览页做成「按片子分组 + 当前成片 + 版本 + 段落首尾帧 + 自检图」，
分镜台留到下一版独立页面。

**代价**：现在只能播 `runs/` 下的 mp4，不能播素材盘原片，也不能按原片时间拖动。
这是已知边界，不假装已经支持。

### D13 单文件 HTML，无构建步骤

**背景**：一个人维护，页面就是一个看板；引入 Vite/React 会多一套依赖、构建和部署。

**决定**：`index.html` 单文件，内联 CSS 和 JS；`#video` 这类 hash 可直达页签；
筛选和展开用事件委托，刷新内容不丢输入焦点。

**代价**：1099 行集中在一个文件里，到分镜台这种复杂页面时应拆分
（可以先按页面拆 `<script>`，再考虑构建）。

### D14 深色监看风（v0.4 起，取代浅色）

**背景**：v0.3 是浅色通用后台。张老师看后说「风格要符合我们的视频行业」。

**决定**：近黑底 `#080b10`、红色品牌点 `#ff4d4f`、四段各一色（蓝 / 紫 / 琥珀 / 绿）、
大号等宽数字、粘性导航；`color-scheme:dark` 让原生控件也走深色。

**代价**：长时间读宽表格不如浅色舒服；素材分析页 10 列表格在深色下更吃对比度，下一版单独调。

> 被取代：原判断「浅色为主，深色待做」（11-13 早）。当时的理由是「先做通用后台、深色以后再说」；
> 张老师一句「符合视频行业」把方向翻过来了。原文保留，不删。

### D15 文案和审核必须拆成两段

**背景**：旧总览的「文案」用的是 `approved / 清单数`。19 条清单只有 2 条过审时，
文案显示 11%，看起来像「文案没写」。张老师要的四段是素材 / 文案 / 审核 / 出片。

**决定**：
- 文案 = 有清单的片子 ÷ 片子目录数（产出）
- 审核 = 清单 approved ÷ 有清单的片子（验收）
- 出片 = 有当前成片的片子 ÷ 有清单的片子（交付）

**代价**：文案很容易显示 100%（清单一到就算出文案），真正的瓶颈会落在审核。
这正是要暴露的：**生成不等于过审**。

### D16 页面不放解释文字

**背景**：底部图例、表头解释、页脚说明都是写给第一次看的人；每天看的人只关心数字。

**决定**：总览只留四段数字与条数；素材分析去掉表头解释；待审文案把两段说明压成一句数字。
解释写进 `docs/UI_技术决策.md` 和 `docs/UI_版本演变.md`。

**代价**：新人第一次看要有人带；换来的是老用户一眼看完。

### D17 实时监看：2 秒轮询 + 局部更新，不整页重画

**背景**：张老师要的是「工作状态监控」，不是「事后结果展示」。
素材处理（OCR / 切镜头 / 打标 / 合表）是分钟级长跑；原来页面 15 秒整页重画一次，
长任务在跑时只看到最终百分比，看不到哪一集、跑了多久、还剩多久。

**决定**：
- `progress.py` 一任务一文件，带 `started_at` / `updated_at` / `pid` / `done` / `total`；
  `read_all` 算 `elapsed_sec` / `eta_sec` / `alive` / `suspect`。
- 素材脚本全部接入：字幕识别（按帧）、切镜头（按集）、合表（按集累计）、打标（按帧）、装配（按任务）。
  文件名带剧名 + 集号/任务名，多部剧同时跑不互相覆盖。
- 长阻塞调用（ffmpeg 装配 / 抽帧）用 `progress.heartbeat()` 每 30 秒 touch 一次，
  避免 3 分钟没有 done/total 更新就被误判成「疑似中断」。
- 页面每 **2 秒**拉 `/api/progress`，只更新 LIVE 面板和徽标；总览每 **6 秒**局部更新四段数字；
  任务完成时素材表才重画一次。
- 运行中的集在素材表里高亮；任务行显示进度、已跑时间、ETA、最后心跳。

**代价**：轮询有 2 秒延迟；`runs/进度/` 是运行态（已 gitignore）；
脚本异常退出若没写 `failed`，3 分钟后判「疑似中断」，需要人判断。

### D18 一剧一行 + 阶段门禁

**背景**：四列逐行表格像报表，每行重复四个阶段名；10 部剧时看不过来。
测试数据里还出现「素材 93% 却已有成片」的倒挂——理论上前一段没完成，后面不该有数据。

**决定**：
- 每部剧一行，行内一条四段进度条；阶段名只在顶部图例出现一次。
- **当前阶段 = 第一个未完成阶段**；它后面的段填充 0、变暗，不显示后面数字。
- 每行只显示当前阶段的主数字 + 明细（素材百分比 / 文案条数 / 审核或出片的 x/y 条）。
- 顶部图例给「当前阶段分布」（素材 3 / 文案 0 / …），不是全局百分比。

**代价**：状态文件里已有的后段数据（测试 / 历史）会被门禁隐藏；
阶段完成判定要严格（素材要求 `pct=100 且集数>0`），否则整条管线会卡在第一段。
查后段证据去「待审文案 / 成片预览」页，不在总览混看。

### D19 剧编号与活动/归档由注册表决定，页面只读

**背景**：一批一批处理剪辑；活动剧编 J1..Jn，归档后号让出、后面的往前补。
同一部剧在不同批次会换号，页面自己按字母序或名字算号，迟早对不上。

**决定**：
- 唯一真源 `runs/剧注册表.json`：`drama_order` + `dramas[].status/code/archived_code/aliases`。
- 服务端 `/api/registry` 出条目；`/api/pipelines|reviews|videos?scope=active|archived` 过滤；
  总览按 `drama_order` 排。
- 页面顶部 **活动 / 归档** 子页签，默认活动；归档行显示 `archived_code` + 「归档」pill + 归档日期。
- 页面不自己编 J 号，也不按字母序重排。

**代价**：归档后会出现两个 J1（归档时的号、活动的新号）；
靠 `status`、归档 pill 和范围页签区分，不靠号本身区分。

### D20 覆盖率与完成度分开：60% 是够用线，不是做完

**背景**：素材分析规则改成「分析全剧 60% 算够」；父爱 18/30 = 60%，
但只有台词，没有镜头标注和合表。

**决定**：
- 页面显示 `cover_pct`（已建台词集数 ÷ 全剧集数），素材段上画 `target_pct`（60%）目标线。
- 阶段是否完成看后端 `done`（三份资料齐到 `target_eps`），**不看 `cover_ok`**。
- 覆盖率达标但缺资料时，明细写「台词 x/y · 镜头 x · 合表 x」，不把阶段往前推。

**代价**：会出现「60% 到了、还停在素材」的显示；需要靠明细解释，不能只看大数字。

### D21 百分比放在阶段段内，不放在行尾

**背景**：行尾一个大百分比看起来像整条管线的总进度，尤其素材 31.7% 会和「整条只做了三成」混在一起。

**决定**：
- 每段显示自己的值：当前段显示百分比 / 条数，已完成段显示 ✓，未到段空白。
- 行尾只留当前阶段 pill + 明细，不再放大数字。

**代价**：段宽有限，长数字要缩写；扫视要靠色块和段内数字，不再有一个「一眼看总进度」的大数。

## 四、边界与风险

- **本机限定**：服务只监听 `127.0.0.1`；没有登录、没有权限模型。要给团队用，先补鉴权，不要直接改 `0.0.0.0`。
- **只读的边界**：只读保护了数据，也意味着页面不能替人做「通过 / 驳回 / 出片」。这些门禁仍在对话里。
- **文件路径是真相**：状态文件写错、成片被挪走、剧名对不上，页面会如实报错而不是猜。
- **样本量小**：3 部剧、6 条有视频的片子。30 部时的分页、搜索性能、列表密度还没验证。
- **历史剧**：原视频不在本机的剧不进管线；它们的清单和成片仍能在预览页看到。

## 五、复用到下一个看板的检查清单

1. 状态从哪来？谁是唯一算法入口？
2. 页面需要写回吗？如果不需要，先做只读。
3. 当前有多少条数据？放大 10 倍后布局还成立吗？
4. 哪个数字最容易被误读？把口径写进页面，不写在口头。
5. 有没有「台账写了但代码没改」的欠账？验收回到产物上数一遍。
6. 慢在哪？先量（stat / read / 渲染），再决定优化代码还是缓存。
7. 哪些动作花钱且不可逆？把它们挡在页面外。
8. 有没有把「产出」和「验收」混成一个指标？
9. 页面上的解释文字，是第一次看的人需要，还是每天看的人需要？
10. 页面上的数字是最终结果，还是运行中的状态？长任务现在跑到哪、跑了多久、还剩多久？
11. 进度文件是不是一任务一文件？多部剧 / 多条片子并发会互相覆盖吗？
12. 前一段没完成时，后一段在页面上是不是空白？还是把测试 / 历史数据也画出来？
13. 编号 / 状态有没有唯一真源？归档后号会重排吗？
14. 覆盖率达标等于阶段完成吗？三份资料齐了吗？
