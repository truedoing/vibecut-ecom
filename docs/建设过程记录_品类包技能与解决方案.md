## 叙事线索（给自媒体用）

这个故事不是「AI 帮人写文案写得更快」，而是三次**优化对象的转移**：

1. 一开始以为瓶颈是**文案生成速度** → 从 15 分钟压到 4 分钟
2. 后来发现瓶颈是**素材** → 实测竞品视频 90 条画面只有 6 条能借
3. 最后发现真正的瓶颈是**知识没有沉淀成结构** → 于是从「写脚本」转向「造技能」

而每一次转移，几乎都由张老师的一句质疑触发。文档里保留了这些原话，
因为它们比结论更能说明判断是怎么形成的。

## 一、起点：一条写了 15 分钟的文案（10-19 ~ 10-20）

### 1.1 第一次调用

需求只有一句：「用 ecommerce-script-gen 生成一条羽衣甘蓝的带货脚本」。

技能加载后出现一个认知差：**技能不是点一下就出稿的程序，是一套指令**。
我按它的六步流程手工执行时，张老师中途打断：

> 「你再干嘛？是在调用 ecommerce-script-gen 技能吗？不要自己去做」

我解释清楚：技能里唯一的可执行代码是 `validate.py`，生成文案本身没有脚本，
只能由模型照着规则写。这个澄清很重要——**「调用技能」和「执行技能」不是一回事**，
后面所有架构讨论都建立在这个认识上。

### 1.2 第一个判断错误：项目级技能读不到

我查了工作区 `/Users/apple/WorkBuddy/2026-10-19-07-50-16/.workbuddy/skills/`，
发现是空目录，就下了结论「项目级技能读不到，ecommerce-script-gen 是用户级」。

张老师反问：

> 「我不理解的是，为什么项目级的技能你读不到？你就是这个项目里的聊天任务呀。」

他是对的。实测项目级技能在
`~/.workbuddy/project-resources/p_fc75b6dc…/skill_*/`，共 4 个平台预置技能，
全部在我的可用清单里。**我把「工作区文件夹」和「团队项目」当成了同一个东西。**

这件事后来还导致一次更大的架构教训，见第四章。

### 1.3 两条脚本，然后爆发

- Task4「算笔账」（拆解算账型，14 段 / 292 字）
- Task7「放到过期」（场景型，14 段 / 240 字）

Task7 出完后，张老师算了笔账：

> 「你自己看看用了多长时间？15分钟。我就剪辑一个一分钟的短视频。你生成文案都用了15分钟。
> 你仔细检查精简一下，没用的逻辑都去掉，比如什么预算之类的。」

复盘发现时间大头不是打字，是**产物结构**：四份文档是照「策划 → 导演 → 生成 → 剪辑」
四个角色分工设计的，而他是一个人剪 60 秒视频，其中两个角色根本不存在。
同一份信息在 `segments` / `evidence_map` / `trust_map` / `conversion_chain` 里存了三遍，
还有一整节在算「5 轮抽卡 ¥50–65」——**片子一张图都还没生成，这些数字全是纸面推演**。

给了三档方案，他选 **B（四份并两份）**，并要「技能本身也要精简」。
产物从 56 KB 降到 21.9 KB。

### 1.4 第二个判断错误：把「提示词延后」当成全实拍

精简时我把 AI 环节整个砍掉改成全实拍，被纠正：

> 「错了，我是说先不生成 AI 提示词，并不是指全实拍。还是原来的 AI 结构不变，
> 还是主 AI 与副 AI 视频配合，只是提示词与参考图提示词等我想下一步生成。」

于是定下**两阶段**，并写进技能防呆：

| 阶段 | 做什么 | 什么时候 |
|---|---|---|
| 一 · 结构 | 定几条 AI、覆盖哪些段、各多少秒、声音方案、用途 | **默认都做**，与写口播同步 |
| 二 · 提示词 | 分镜序列提示词 + 两张参考图提示词 | 他点名才做 |

理由原话级：**镜头结构属于文案设计的一部分，事后补会推倒重来**。
实现上用 `prompts_pending: true`，`prompt` 留空、`negative_prompt` 现在就填，
校验器识别该标记跳过长度检查；填了 prompt 还留标记会反警告。

## 二、第一次转移：从「写文案」到「出片」（10-20）

### 2.1 三种出文案方式，但问题问错了层

张老师列了三条路：① 对标爆款洗稿 ② 借鉴常见结构 × 角度人群 ③ 完全创意化。

我逐条拆完，给了一个更根本的判断：**优化错了环节**。

| 环节 | 耗时 | 文案提速能省多少 |
|---|---|---|
| 出文案 | 4–5 分钟 | 全部省掉也只有 5 分钟 |
| 拍摄 | 1–2 小时 | 0 |
| 剪辑 | 30–60 分钟 | 0 |

**文案环节全免费，也只省下总耗时的 5%。** 大头在素材。

### 2.2 素材路线：一次实测推翻假设

他明确：

> 「素材我们不拍，不要再提拍的事，都是从别的视频中截取」

我原以为素材池是空的，结果查出 `semantic_metas.json` 里躺着 **164 条已用 VLM 描述好的
镜头片段**（15 条参考视频，90 条 vlm 画面 + 74 条 asr 台词）。素材已经索引好了。

然后严格筛了一遍：

| 判定 | 条数 | 时长 |
|---|---|---|
| ✅ 严格合规可借 | **6** | **23.6 秒** |
| ❌ 含人物 / 产品 / UI / 认证 | 84 | 372.6 秒 |

而这 6 条再核对，**5 条还是别人的产品**（「福满椰羽衣甘蓝海盐燕麦片」）。

> **悖论**：竞品带货视频里几乎每一帧都是他们自己的产品。能借的只有「不出现产品」的
> 过场镜头，而过场镜头本来就没几秒；有辨识度的画面恰恰最不能用。

中途还犯了一个错：第一次判定把 164 条混在一起筛，列出来的大多是**台词转写**不是画面描述。
**用前先按 type 分开**——这条写进了项目记忆。

转向通用素材站（Pexels / Pixabay / Coverr / Mixkit，CC0），四层获取策略成型。
**那 74 条 ASR 台词反而成了元素库的金矿**：画面不可借，但七条竞品完整台词能抽出
钩子型、痛点说法、价格话术、CTA。

### 2.3 第三个判断错误：只提钩子库

我建议「丰富钩子库」，他质疑：

> 「可以 丰富钩子库，但是为什么只提钩子呢？痛点库或者别的不重要吗？」

这个质疑是对的。我一直戴着「完播率」眼镜看脚本（前 3 秒决定划不划走），
那是**投放视角**，不是**产能视角**。

正确分界：**跨品类复用看钩子，同品类矩阵看痛点与场景。**
产品不变时，痛点池和场景池是有限可穷举的——穷举出来就是产能，复用价值比钩子高。

于是建了**七库**：钩子 / 痛点 / 场景 / 论据 L1–L4 / 信任 T1–T3 / CTA / 金句，
外加价格话术库。三份资产落地：`素材获取清单.md`、`元素库.md`、`角度×人群矩阵.md`。

### 2.4 轻量文案档

「三个出在一个文档中，每一类只包括文案脚本，我要发给别人看」→
区分了**执行档**（JSON + 拍摄执行单，过校验器，自己用）与**文案档**
（一个 md 多条合订，只有口播，发外部）。

随后追加「文案结构也标一下，就是钩子，痛点啥的」，改成三列表格
「段 | 结构 | 口播」，十个标签。加结构列真正的用处不是让人看懂，
是**让人改的时候知道边界在哪**（图例里写死了「证据四类必须轮换，相邻两段不得同类」）。

## 三、第二次转移：平台与人群（10-20 ~ 10-21）

一句「我们现在投放的是微信视频号，所以目标用户年纪大些」把整套参数改了：

| 维度 | 抖音 | 视频号中老年 | 中年女性 | 给妈妈买 |
|---|---|---|---|---|
| 语速 | 4.5 字/秒 | **3.8** | **4.1** | **4.3** |
| 钩子 | 冲突 / 网感 | **认人认事认场景** | **认出自己** | 子女视角 |
| 转化 | 先买一盒试试 | 让孩子们帮你看一眼 | 允许自己 | 带回去 / 别等过年 |

四版文案档产出，六型角度由两版互补占满。

**「给妈妈买保健品类」这次踩到硬红线**：产品是普通食品，
「保健品」三个字一旦进文案就是暗示保健功能，且子女替妈妈做使用证言风险更高。
处理是**情感定位保留、产品身份表述整个拿掉**，指代用「那些瓶瓶罐罐」「一瓶几百的」。
配套两条：不替妈妈做使用证言、孝心不能当功效包装。

这四套参数后来成为技能自带的 `platform-audience.md`——
**它是平台属性不是品类属性**，卖什么都一样，所以不进品类包。

## 四、第三次转移：团队共享（11-03 上午）

三个连问：

> 「技能更新了吗？有没有安装在项目空间。我添加项目成员对方能自动使用吗？」

查官方文档后，答案很明确：

- 「项目配置（指令、Skill、专家、连接器）**保存在云端中，项目成员共享**」
- 「Web 端和客户端的**个人 Skill 库互不相通**」
- 任务中 Skill 选择范围：「**项目 Skill + 已安装的 Skill + 现场导入的 Skill**，项目 Skill 置顶」

→ **只有项目 Skill 随项目共享，个人 Skill 不共享。**
→ 技能启用/关闭状态记在**个人全局配置**，成员那边还得确认开着。

更要紧的是我加的一条判断：**能调用 ≠ 能跑通**。
`ecommerce-script-gen` 的 SKILL.md 写死 `/Users/zgl/VIBECAP`，VIBECAP 的数据
（15 条参考视频、语义索引、文案资产）全在本机，不在项目资料库。
成员装上项目 Skill 后能看到技能，但流程第 1 步「读 `projects/{项目名}.json`」直接断，
**而且报错不会提示是路径问题**。

这直接推翻了 10-19 的结论。那时我说「保持用户级是唯一跑得通的组合」，
前提是**只有一个人用**；现在前提变了，结论反过来：该做成项目 Skill，
但必须先去绝对路径化（同时也是 Windows 交付的硬要求）。

## 五、架构决策：四个独立技能 + 共享台账（11-03）

张老师给出完整目标：

> 「我的目的是构建几个独立的技能，比如文案的、比如视频的、然后通过后台支持服务 vibecut
> 给串起来一个工作流，并且支持项目团队，当然每个人单独做自己的视频任务。整个流程就是
> 厂商提供素材，我们自己创建文案并生成开头的钩子 AI 视频，然后混剪厂商提供的素材。」

### 5.1 通用技能还是品类技能

结论：**一个通用技能 + N 个品类包**，按能力拆，不按品类拆。

理由是组合爆炸：按品类建，N 个品类 × M 个能力 = N×M 个技能；改一条合规规则要改 N 遍。
判据只有一条：**流程不同才拆技能，数据不同不拆**。
羽衣甘蓝粉和果子酱的差别（配料、合规词表、素材索引、话术库）全是数据，
流程（六型角度、举证配额、结构标注、字数语速、合规扫描）一模一样。

顺带确认了 **1 × M 而非 N × M**：文案 / 视频 / 剪辑按能力拆，由 vibecut 编排。

### 5.2 输入输出契约

| | 现在 | 改造后 |
|---|---|---|
| 输入 | 隐式读本机目录 | 显式 `category` / `angle` / `audience` / `brief` |
| 输出 | 写固定目录 | 返回结构化结果，落库由 vibecut 决定 |
| 消费方 | 人看 md | vibeCut 直接消费 JSON |

**最容易漏的一条依赖：角度唯一性。** 现在判断是否撞角度靠扫本机 `tasks/` 目录，
团队化后每人扫自己的目录**必然撞角度**。这必须从「文件依赖」变成「服务依赖」——
由台账提供查询。这是多人协作不撞车的唯一办法。

### 5.3 第四个判断错误：vibecut-ecom 的性质

我上一轮说「对齐现有 `/ecommerce/refs` 接口」，被纠正：

> 「注意我说的是 vibecut-ecom 就是一个准备新开发的电商定制版 /Users/zgl/vibecut-ecom，
> 不用参考现在的 vibecut。」

实测 `/Users/zgl/vibecut-ecom` 是 11-02 新建的独立仓库（M1 已完成），
CLAUDE.md 写死：旧 VIBECAP **已冻结**；新仓库定位是
「素材库 + 去字幕 + 任务台账 + 版本审核」，**不剪片子、不做时间轴**。

> 原话：「**Agent 是编剧和外包，VibeCut 是片场和资产库。**」

所以技能之间**不是调用链，是共享同一个台账**——「留接口空间」的形态不是 REST API，
而是 **CLI 命令契约**（`skills/vibecut/SKILL.md` 已定义）。
硬规则还有：SQLite 唯一真源、媒体永不上传云端、**Windows 是第一交付目标**。

### 5.4 四个拍板

| 决定 | 落点 |
|---|---|
| 1 品类包放项目资料库 | tdrive 放**只读规则层**；素材本体走 `assets ingest` 留本地 |
| 2 保留文案档、人要审核 | 五状态含「待审」+ `versions`/`reviews` 表已在；技能只标状态不碰流转 |
| 3 角度查询留接口 | `vibecut task list --project <品类>`，不新建表、不本地扫目录 |
| 4 虎坚果酱做第二个品类 | 验证通用性 |

**边界划清**：tdrive 是共享知识层（纯文本只读），SQLite 是运行台账层，
两者记的不是同一件事，不违反「唯一真源」。

## 六、概念澄清：品类包到底是什么（11-03）

张老师问：

> 「动手前，我还不是太明白，产品包是什么意思？就是产品信息是吧」

用实物对照最清楚：`projects/羽衣甘蓝.json` 全部只有 **8 行**
（name / type / reference_videos_dir / product_text / fps / description）——
这就是「产品信息」的全部。而要让通用技能跑出合格脚本，还缺话术元素库（127 行）、
品类合规扩展、素材索引、待填项。

**判据一句话：换个品类会不会变。会变的进品类包，不变的进技能本体。**

同时我纠正了自己上一轮的一处错：把「平台 × 人群参数」（3.8 / 4.1 / 4.3 / 4.5 字每秒）
列进了品类包——**那是平台属性不是品类属性**，该放技能自带的共享参数表。

### 6.1 合规尺度：最重要的一次纠正

第一版我把厂商卖点逐条判了「禁用」，张老师明确纠正：

> 「你不要太严格，商家提供的卖点，你可以换种更合适合规的方式话术，但不要直接不用，
> 我们毕竟是商家不是监督局，首要任务还是促销。」

我确实把商家的活干成了审核的活。正确做法是**保留商业内核，替换风险谓语**：

| 风险谓语 | 换成 | 例 |
|---|---|---|
| 身体功效结论 | 成分 / 数值 / 用量画面 | 饱腹感强 → 一勺能抹满一片面包 |
| 比较宣称 | 自述特点 | 媲美橄榄油 → 每100g omega-9 33.1g |
| 健康暗示 | 场景 / 口感 / 配料 / 产地故事 | 每日营养 → 早抹面包午拌面晚拌酸奶碗 |
| 无依据换算 | 加「按…折算」+ 出处 | 一勺≈15颗松子仁 → 按《中国食物成分表》折算 |

**真正要避的只剩四类**：疾病功效、无依据虚假比较、无认证宣称、虚假价格稀缺，
外加过敏原反向宣称这条安全底线。**禁词表从写作起点降级成兜底检查。**

品类包里那张表因此从「厂商原话禁用清单」改名为**「卖点话术转换表」**
（原话 → 可用说法 → 依据/条件）。这不是妥协：改写落点「场景/口感/配料/数字/产地」
正好是视频号中老年最吃的五类，**把说服力从身体改善挪到生活场景，是挪到更容易成交的地方**。

### 6.2 十张图与两次核对

- 第一张卖点图：正式品名「沙漠一号 油莎豆坚果酱 150g」、配料自述、产地、价格、
  **过敏原提示**（生产线加工花生芝麻）
- 八张详情图：带来**数值与出处**——每100g 膳食纤维 9.2g / 维E 7.32mg / omega-9 33.1g，
  换算依据《中国食物成分表第六版》与 USDA/FSANZ，1 勺 = 15g
  → 大部分卖点根本不用砍，念数字比喊「富含」更有信任感
- 两张包装实拍：**正面标定品名「虎坚果酱」与规格 150g**，
  **背面标补齐正式营养成分表**，数值与详情图完全一致 → 升为 `verified: true`；
  还拿到保质期 9 个月、开封冷藏 2 周内吃完、致敏物质正式标注

一个反常识发现：脂肪 44.9g/100g、能量 2449kJ，厂商却写「轻盈无负担」——
不只是违规，是**跟自己的标签打架**。但对抹酱来说高脂肪就是香、就是耐吃：
改成「一勺就够，抹得开，一罐能吃很久」，把劣势转成用量 + 性价比，比删掉卖点强得多。

## 七、最后一环：建包独立成技能（11-03）

张老师拍板：

> 「这个品类包的创建其实还是挺重要与复杂的，这个应该是一个独立的技能，可以重复使用。」

这个判断补上了我漏掉的第一环。技能链由「文案 → 视频 → 剪辑」修正为
**建包 → 文案 → 视频 → 剪辑**。三条理由：

1. **低频高杠杆**：建包一个品类一次，但包错一处，这个品类下**所有**文案全错
2. **判断类型不同**：建包是事实判定 / 合规分级 / 冲突核对；文案是角度 / 结构 / 举证配额。
   混在一起文案技能会重新变胖——正是 10-20 他嫌「56KB / 15 分钟」的同一种病
3. **团队价值在能力不在文件**：成员真正需要的不是「能读到品类包」，
   是「拿到一堆厂商图也能造出标准包」

三条硬设计，全从这次实战里长出来：

- **`verified` 双来源标记**：厂商卖点图 ≠ 正式标签；文案技能只读 `verified: true`，
  未核实自动转占位符 → 从根上挡住编造数字
- **`blocking` 分级**：卡不卡配音分开标
- **冲突不自动选值**：150/230/108 打架，产出清单交人定

产出流程：**本地 draft → 人审 → 明确确认后才上传 tdrive**（写操作须确认）。
只放只读知识，不记角度占用 / 任务状态（那是 vibecut 台账）。

### 8.2 校验器抓到的两个真实缺口

第一次跑羽衣甘蓝包，报了 2 ERROR：
`pf_002`（产品类别）与 `pf_010`（过敏原）`value: null` 却没有 placeholder。

但这两条**根本不进口播**。修的是规则不是数据：

> 只有 `usable_in_copy: true` 或 `blocking: true` 的字段才必须有占位符；
> 其余允许无占位符，但 `verified_note` 要写明为什么无需。

这正是「校验器应该表达业务语义，不能一刀切」的实例。修完两包均 **0 ERROR / 0 WARN**。

## 九、验证中暴露的技能不足（四处回改）

这部分最有案例价值——**通用性不是设计出来的，是被第二个品类逼出来的**。
四处全部是文档层补充，**没有改 schema 字段**：

| # | 暴露的问题 | 回改 |
|---|---|---|
| 1 | `field` 枚举没有 `brand` / `manufacturer` / `claims_zero_add` | 改成「建议值可扩展」并补上这三个，要求 `label` 写清、不得与已有字段重复 |
| 2 | `script_design` 被用来承载「厂商吃法清单」，语义勉强 | 在 schema 里写明它也可用于自用素材，但 `verified_note` 必须写明「不是厂商事实断言」 |
| 3 | 四层 A–D 的名称在 `vendor_provided` 下不成立（A 不再是通用素材站） | SKILL.md 第 7 步加对照表：**代号固定、名称按 mode 调整**，B 层硬约束不随 mode 变 |
| 4 | `conflicts` 只举了数值打架与口径冲突 | method.md 补第三类「**厂商话术与正式标签自相矛盾**」——最易漏，因为是同一个厂商自己打自己 |

第 4 条尤其值得记：虎坚果酱「轻盈无负担」vs 标签脂肪 44.9g 不是两个来源不一致，
是**同一个来源内部矛盾**。发现后草稿先绕开（改用用量话术），但 `status` 仍保持
`open` 交人裁决，不替厂商决定。

## 十一、可复用的方法论提炼

1. **流程不同才拆技能，数据不同不拆** —— 避免 N×M 组合爆炸
2. **换个品类会不会变** —— 划分「包」与「技能本体」的判据
3. **能调用 ≠ 能跑通** —— 共享机制与依赖路径是两件事
4. **商家视角、促销优先** —— 合规是「怎么说」，不是「能不能说」
5. **产物体积要配得上传达的分量** —— 角色分工的文档结构只适用于真有那些角色时
6. **从实例归纳技能，再用技能验证新实例** —— 规则必须能解释第一个样本
7. **校验器检查结构，不替人核实事实** —— `verified` 是人的责任，不是脚本的
8. **冲突不自动选值** —— 低频高杠杆处，把裁决权留给人
