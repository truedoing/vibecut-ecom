## 一、背景：这个专题到底在解决什么

甲方指定同一部短剧，全网都在剪同一批素材。约束是死的：零解说纯剪、原剧台词保留、
不去原剧硬字幕、音频不做、AI 二创最多十几秒。能动的只有剪辑结构和画面渲染。
目标不是「百分百躲过检测」，是在**固定素材**的前提下把画面重复读数尽量往下压。

两条红线自始至终没破：**不去字幕**；**去重的权重小于剪辑叙事质量**，
不能为了降重去动段序、段长、台词、五幕，也不能为了字幕去多选一段戏。

## 五、为什么做成「副本入库 + 原件保留」两套

**背景**：报告和成片原本全在 `build/` 下面，而 `.gitignore` 把 `build/` 和所有 mp4 都排除了。
也就是说，这几轮最值钱的证据**完全不受版本控制保护**，将来一次「清理生成的视频」就可能全没。

**转折**：想过改忽略规则给这个目录开白名单，但 `build/` 是全局规则，
放开会把别的片子、别的任务的临时产物一起放进来，范围收不住；
也想过把成片一起入库，356 MB 视频进仓库不合适。

**结论**：小而关键的报告、报告引用的图、生成脚本、参数表复制一份到 `docs/去重专题素材/`
纳入版本控制；大体积成片留在本地，用**六处标记 + 这份总账 + 23 条路径登记**保护。
原件一个没动、一个没删。

**边界（如实交代）**：入库副本是 **2026-11-14 定版快照**，不会自动跟着原件变。
下一轮迭代改了原件之后，重跑一次 `同步快照.py` 刷新副本和清单即可，脚本只增不删。

## 七、方法论（这一节是留给讲课和自媒体的）

按制度写「背景 → 转折 → 结论 → 方法论」，挑六条最值得留的：

1. **判断一件事归产线哪一步，别看哪一步顺手，看哪一步握着做这个判断所需的信息。**
   渲染那一步只有时间码，只有文案那一步知道哪句是高潮、哪句是收尾。
2. **自动对齐能算准「哪句最狠、在第几秒」，算不出「这句打上去会不会和画面里已有的字打架」。**
   前者归数据，后者归人眼。能用数据自动化的边界在哪，本身就是一课。
3. **以为在三种处理办法里选，其实是在两种内容形态里挑。**
   前提没问清，选项就会排错方向（金句 = 原台词，还是也可以概括升华）。
4. **「有几种动效」和「什么时候用哪种」是两件事。**
   只堆样式、不建分配规则，结果还是一套用到底。
5. **技术方案早写死的口径，预览阶段为省事没执行，全片阶段还是得补上。**
   一次编码 vs 二次压制，不是审美问题，是交付物能不能用。
6. **把迭代过程当资产，就得连「它放在哪、会不会被忽略规则扫掉」一起设计。**
   这次最险的不是某个效果没做好，是六轮证据全躺在一个被排除的目录里。
   **证据链的保护本身，也是工程决策。**
