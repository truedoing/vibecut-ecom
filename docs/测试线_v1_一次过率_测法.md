# 测试线 v1：先测「一次过率」，再写代码

> 2026-11-12 建。依据 `docs/短剧链路_v0.4_批量管线架构.md` 第四节：
> 「一次过率没有数据，后面所有架构讨论都是在赌。」
>
> 这条线不写产品代码。它只干一件事：**跑真实流程、记真实数据、把那个数拿到手。**

## 〇、v1.1 修订（2026-11-12，张老师定）

三条改动，从第 01 轮起执行。

**1. 每轮测试开始前清空台账，之前生成的一律不算。**

原话：「每轮测试把台账清理一下，原来生成的不算，就当没生过。」

做法：台账只装当前这一轮的行，不跨轮累计。一轮结束把 `台账.csv` 复制成
`轮NN_台账.csv` 存底，再清空（留表头）。这样每轮的过率都是干净的，
不会被上一轮的失败拉低，也不会被上一轮的成功抬上去。

**2. 片子规格：主线档，4–6 分钟（原先是副线 2–3 分钟）。**

原话：「时间偏低，要 5 分钟左右。」

后果要说清：**一部长剧的素材大约只够出 1–2 条 5 分钟的片子。**
八零憨妻 20 集 26.8 分钟，出到第 5 条就到底；以真心守护至亲 17 集合规素材
只有 15.3 分钟，被 D1/D2 用掉 6.4 分钟后，连三条 5 分钟都排不出来（差 364 秒）。
这不是排法问题，是素材总量问题。

**3. 记时间：机器侧耗时用打点，人审耗时用台账，两者分开。**

- 机器侧：`python3 runs/测试线/打点.py start/mark/end/show`，记每个环节真实耗时
- 人审侧：台账的「开始审 / 审完 / 人审分钟」三列

为什么分开：这两个数回答的是不同问题。机器侧决定「单条管线能不能更快」，
人审侧决定「一个人一天能审几条」——后者才是 20 条/天的真正上限。

**4. 已作废的轮次**：第 0 轮的 B1（T9001–9003）、B2 初版（T9004–9006）不计入任何统计，
文件留着只作流程留档。

## 一、要回答的问题

**按现在的技能，一条片子第一版就有多大概率能过？**

为什么它排在所有事情前面：

- 「一天 20 条」要成立，一次过率得稳在 50% 以上。
- 如果只有 30%，那天根本做不完——该优化的是选题质量，不是并发数。
- 这个数现在一条数据都没有。九版混剪那条不能当返工率用，那是从零建方法论的成本。

## 二、怎么测：不新建流程，就跑现在这套

**关键一条：测的内容必须由现在真实在用的技能产出，不能由我代笔。**

如果我手工写三份文案给你审，测出来的是「我写文案的过率」，不是「技能出文案的过率」。那个数对未来没有任何指导意义。

所以流程还是老的：script 技能六步，出方向卡 → 排清单 → 出文案。区别只有一个——**不在中间停下来等你，一口气跑到文案，再叫你看。**

## 三、测哪几条

**第一批 3 条：`T9001`–`T9003`，全部用「八零憨妻的甜蜜日常」。**

| 决定 | 为什么 |
|---|---|
| 用这部剧 | 库已建好（20 集台词、19 集素材索引），**不用建库**，只测文案环节。成本最低 |
| 3 条不是 5 条 | 3 条正好是一次真实批次的大小（一剧 3 选题）。凑 5 条会破坏批次结构，算不出「整批过率」 |
| 选题由技能出 | 已经用过的角度（门、账、婆婆、力气、标签线）给它避开就行，但**不预先圈定这次写哪个** |

测完 3 条看数，不够再加第二批 2 条（`T9004`–`T9005`）。

**编号规则**：`T9001-P1`，`P1` 是文案审，`P2` 是成片审。剧场号 **90 段留给测试**，正式剧从 01 开始，永远不会撞。格式跟生产编号完全一样，将来工具不用改。

### 3.1 方向卡那一次「停」怎么办（建线时发现的缺口）

现在的技能第 1 步出方向卡（2–3 条线），**等人圈定才排清单**。这是写在技能里的一道人工确认。

测试线要一口气跑到文案，这一停就必须处理，而三种处理方式测的东西完全不一样：

| 做法 | 测出什么 | 代价 |
|---|---|---|
| 让你先圈 | 还是「人在中间」的老流程 | 测不出合并审，等于没改 |
| 技能自己拍，不存档 | 能跑通，但不知道它拍得对不对 | 方向错了要跑完才发现 |
| **技能自己拍，把三张卡全存档** | 既不停，又能拿到「自决命中率」 | 几乎零成本 |

**取第三种。** 每批跑完存一份 `runs/测试线/B1_方向卡对比.md`，里面三张卡原文 + 技能实际选的那条 + 你事后看「如果让我圈我会圈哪个」。

这个数比一次过率更早决定架构能不能成立：

- 命中率高（比如 5 次对 4 次）→ 这一停可以安全去掉，「人只在末尾」成立
- 命中率低 → 这一停不能去，v0.4 的「人只审文案」这个前提要重估

**它其实比一次过率更要命**：一次过率低只是产量打折，方向卡自决不能做，是整个地基不成立。

## 四、「一次过」怎么判——必须先定，不能边看边改

这是整条线最容易做坏的地方。**如果过不过由当场感觉决定，测出来的是心情指数，不是过率。**

### 4.1 送审前，机器先查五项

（现在没有自动检查，先手工跑。跑完就知道该怎么写成脚本——这就是这段的副产品。）

| # | 查什么 | 不过的后果 |
|---|---|---|
| 1 | 每段出点没超过这一集的**视频流时长** | 装配时必然报错（容器时长比视频流长 0.6–0.8 秒） |
| 2 | 引用的台词句子在台词库里**真有** | 切出来对不上，或者切半句 |
| 3 | 同一集连续段数 ≤ 2 | 踩平台「大段拼接原片」 |
| 4 | 总时长在区间内 | 太短没内容，太长没人看 |
| 5 | 三个选题**撞不撞车** | 三胞胎，白审一轮 |

**机器拦下来的也要记一行**：判定=不通过，谁判=机器。这样能算出「机器能替你挡掉多少」——那个数直接决定人审量能降多少。

### 4.2 你审的时候判什么

看清单 + 抽几段看画面，判这五条：

1. 五幕齐不齐
2. 每段是不是一个完整的小冲突（挑起 → 交锋 → 落点）
3. 前 45 秒有没有一次拒绝、或一次反击
4. 有没有切半句
5. 没看过原剧的人，不靠解释能不能看懂这场在争什么

**只要你想改一刀就不算过。** 挪一段顺序、改一个字幕卡位置，都算。

## 五、记什么：每轮审核一行

表在 `runs/测试线/台账.csv`。

| 列 | 填什么 |
|---|---|
| 编号 | `T9001-P1` |
| 批次 | `B1` / `B2` |
| 剧 | 八零憨妻的甜蜜日常 |
| 选题 | 技能给的角度名，一句话 |
| 版本 | 第几版，从 1 开始 |
| 谁判 | 机器 / 人 |
| 开始审、审完 | `HH:MM`，不用到秒 |
| 人审分钟 | 审这一版花了几分钟 |
| 判定 | 通过 / 不通过 |
| 返工类型 | 六选一，见下表 |
| 具体意见 | 一句话，你自己看得懂就行 |
| 流程卡点 | 这轮撞到什么「没工具 / 要手改 / 要等人」 |

**返工类型只有六种，别自己加：**

| 类型 | 什么算 |
|---|---|
| 结构 | 五幕不齐、因果断链、顺序错 |
| 选段 | 该选的没选、砍错场、开场不抓人 |
| 切点 | 切半句、黑场、出入点超限 |
| 角度 | 跟别的选题撞了、或不是这剧最强的角度 |
| 节奏 | 太长、太拖、密度不够 |
| 事实 | 台词对不上、人物关系错 |

**为什么必须分类**：八成返工都是同一类，优化才有靶子。不分类，最后只会得到「这批不行」这种没用的结论。

## 六、怎么算

```
python3 runs/测试线/算账.py
```

出这几个数：

| 数 | 怎么算 |
|---|---|
| 单条一次过率 | 第 1 版就通过的条数 ÷ 进审条数 |
| 整批过率 | 一批 3 条全部首版通过 ÷ 批次数 |
| 平均轮次 | 总审核行数 ÷ 条数 |
| 机器预检拦截率 | 机器判不通过的条数 ÷ 总条数 |
| 平均人审分钟 | 你审一版平均花多久（直接进 20 条/天的账） |
| 返工类型分布 | 哪类问题最多 |

## 七、数出来之后怎么判（先定，别事后解释）

| 单条一次过率 | 判断 | 该动什么 |
|---|---|---|
| **≥ 60%** | 20 条/天有戏 | 直接上并发和 UI |
| **40–60%** | 勉强 | 先把人审压到 3 分钟内，同时收紧选题 |
| **< 40%** | 20 条/天不成立 | 停下来改选题和文案，别碰并发 |

**样本量的实话**：3 条只是第一个信号，百分比误差很大——过 2 条就是 67%，过 1 条就是 33%。真要下结论得累积到 9–12 条。

所以第一批的目标不是「定生死」，是**验证这条线能不能跑通、第一个信号是正还是负**。

## 八、这轮测不出什么（范围边界，别拿它当全链结论）

| 测不出 | 原因 |
|---|---|
| 建库成本 | 八零憨妻库是现成的。那 2.5–5 小时一块完全没覆盖 |
| 换剧的问题 | 同一部剧连出 3 条，比换一部新剧容易得多。跨剧要另开一轮 |
| 并发问题 | 这轮手工串行，没有调度器。9 条同跑会撞什么，不知道 |
| 成片环节 | 只到文案（P1）。P2 要等真出片 |

回头拿这轮数据论证「20 条/天可行」，记得它只覆盖了文案这一段。

## 九、这轮最大的产出，可能不是那个百分比

手工跑 3 条，一定会撞到：这里要手改一个 json、那里没有工具、这里技能停下来问话。

**这些卡点就是 v0.4 的真实待办清单，不是我想象出来的。** 每撞一个就记进「流程卡点」列。跑完 3 条，写代码的顺序自己就浮出来了。

这就是「测试驱动」在这个项目里的意思：

> **先手工跑一遍，让流程自己暴露哪里不通，再决定写什么。**
