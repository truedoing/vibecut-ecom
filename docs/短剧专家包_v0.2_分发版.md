# 短剧专家包 v0.2.0：做成可分发版

> 2026-11-15。从「只能在本机用」到「拷到另一台机器装完就能干活」。
> 该记的不是文件清单，是三个决策和它们各自挡住的那个坑。

## 一、起点：v0.1.0 是个空壳

v0.1.0（11-10）的定位很明确：**技能是引用，不是副本**。
8 个技能源码在工作仓库 `skills/`，用户级 `~/.workbuddy/skills/` 建软链，
专家人格文件里写一行「仓库根 = /Users/zgl/vibecut-ecom」就完事。

这么定是对的——`short-drama-trailer` 用户级曾经是复制版，改仓库不生效，
查了半天才发现改的是副本。单一真源救了这一类问题。

代价当时也写下来了，只是没解决：**包离开这台机器就是个空壳**。
包里只有人格文件、头像、配置，没有任何一行能执行的东西。

11-15 张老师决定发布到另一台机器，这条欠账到期。

## 二、转折：直接加 `skills/` 会坏两件事

最直觉的做法是把 8 个技能复制进包的 `skills/`，在 `plugin.json` 补 `skills` 字段。
动手前先查了两件事，都不同意这个做法。

**第一件：WorkBuddy 会自动加载插件目录下的 `skills/`。**
翻本机内置插件就看到了——`workbuddy-builtin` 那一堆 `skill-xxx` 插件，
`plugin.json` 里根本没有 `skills` 字段，但目录下都有 `skills/`，技能确实被加载了。
是约定式扫描，不是靠字段声明。

这意味着：包内放 `skills/`，装到哪台机器都会被当成插件级技能加载，
和用户级同名技能重复。**同一套技能出现两份，谁生效说不清**——正是 v0.1 想避免的病。

**第二件：脚本的根目录推导会指错地方。**
技能脚本里 13 处都是这个写法：

```python
ROOT = Path(__file__).resolve().parents[3]
```

`<根>/skills/<技能>/scripts/x.py` 往上三层刚好是仓库根。
一旦换成 `<插件目录>/skills/<技能>/scripts/x.py`，往上三层变成插件目录，
`runs/`、`packs/`、`assets/` 全部找不到——不是报错，是静默地找不到东西，
比报错难查得多。

改 13 处推导也行，但那等于为了分发去动一套已经跑通 12 条片子的生产代码，
风险和收益不成比例。

## 三、结论：包内叫 `skill_src/`，由安装脚本铺到工作仓库

```
包内 skill_src/（8 个技能副本）
    ↓ install.py
工作仓库/skills/（真正的执行位置，脚本根推导照旧）
    ↓ 软链
~/.workbuddy/skills/（用户级技能入口）
```

三条好处：
1. 技能实际执行路径永远在工作仓库里，**13 处根目录推导一行都不用改**。
2. 包内目录名不触发自动加载，不会出现两份同名技能。
3. 与本机架构完全一致——本机是软链指向仓库，新机器也是，没有两套逻辑。

代价：多一步 `install.py`。但这一步顺便把 `.env` 模板、目录骨架、
空工作台都补了，等于把「新机器第一次开工要准备什么」这件事本身也自动化了。
比让用户照着 README 手敲五六条命令好。

## 四、顺手清掉两处写死的本机路径

发布前扫了一遍 `grep /Users/zgl`，技能里还有两处：

| 位置 | 性质 | 处理 |
|---|---|---|
| `asset-index/scripts/cut_index.py:29` | 只是注释里的示例命令 | 改成 `<素材根>/...` |
| `script/scripts/epdur.py:67` | **真实兜底逻辑**：找注册表失败后去 `/Users/zgl/选择`、`/Users/zgl/短剧` 找 | 先读 `.env` 的 `SHORT_DRAMA_ASSET_ROOT`，老路径降为最后兜底 |

第二处是真问题：换机器后注册表（`config/drama-sources.json`）里全是老机器的绝对路径，
兜底路径也不存在，找素材会直接空手而归。
改成读 `.env` 后，换机器只改一行 `SHORT_DRAMA_ASSET_ROOT` 就够。
实测本机仍解析到 `/Users/zgl/短剧/父爱跨越山海`，行为没变。

老路径没删干净是对的——本机历史目录还在用，删了反而断。

## 五、验证：造一台干净机器，不许自己骗自己

「打包成功」不等于「装得上」。所以做了一次完整模拟：

```
临时目录当新机器
  → 解压 zip（54 个文件，659 KB）
  → WORKBUDDY_CONFIG_DIR 指到临时位置
  → python3 install.py --repo 临时仓库
  → 跑 check_env.py
```

结果：**8 项通过 / 2 项待修**，两项分别是「素材根目录存在」「出片密钥已配置」——
这两项本来就该由人填，不是安装问题。
再跑 `status_overview.py`，技能在临时仓库里正常执行，根定位正确。

这一步不做的话，很容易出现「我这儿好好的」，到另一台机器上全线报错。

## 六、方法论：分发的边界在哪

这次最值得记住的一句：

> **专家包只带「怎么干活」，不带「干到哪了」。**

- 改剪辑做法、改技能 → 重新打包，另一台跑 `install.py --force`
- 换素材位置、换剧 → 改 `.env` 和 `config/drama-sources.json`
- 进度、剧集包、素材索引 → 跟着 `runs/`、`packs/`、`assets/` 走

这三件事混在一起，就会出现「专家装好了但接不上上次的活」这种最难解释的故障。
`INSTALL.md` 开篇就按这个边界分成了 A/B 两条路径，先让人自己对号入座。

另一个副产品认识：**判断能不能分发，看的是「包解开后有没有一行能执行的东西」，
不是看包里有多少文件。** v0.1.0 包里文件也不少（人格、头像、配置），照样是空壳。

## 七、本次未做的

- 没动 13 处 `parents[3]` 根目录推导（评估过，收益不值风险）。若将来技能要独立于仓库运行，
  才需要统一改成「环境变量 → 找标志文件 → 兜底」的查找法。
- 没把 `skill_src/` 和仓库源码做自动同步校验。现在靠人记着「改仓库那份，改完重新打包」，
  有分叉风险。可以做一条 `--check-drift` 比对，暂未做。
- 第二台机器上的真实安装还没跑过（只在本机模拟环境验证）。
  真出问题时，`INSTALL.md` 末尾的「出问题了看这里」是按模拟环境里踩到的点写的，
  真实故障可能要再补。

## 八、翻案：v0.2 当天就作废，v0.3 改回「包内自带」

**上面第一到七节是 v0.2.0 的方案，当天晚间被推翻。原文保留，不删。**

### 背景：我以为已经解决了

v0.2.0 做完，验证也跑了，我给张老师的汇报里写的是「可分发版本，装完能干活」。
他的三个回问直接把它判了死刑：

> 1. WorkBuddy 没有官方的安装本地专家的机制吗？怎么还运行起命令行了？
> 2. 所有的东西都应该在安装包里面，怎么还出现分布在不同的目录下呢？
> 3. 我要求的效果就是傻瓜式安装……这个包是给非技术人员用的。

三条全中要害，而且第 1 条是我本该先查的。

### 转折：官方机制一直存在，是我没找

回头查 WorkBuddy 本体，全都有：

- `exportZip` / `installExpertZipFromPath` / `importExpertFromUrl`——
  导出、从本地 zip 装、从分享链接装，还带安全扫描。
- 技能的「上传技能」支持 `.zip / .tar.gz / .tgz / .skill`，从 zip 里的 SKILL.md 解析元数据。
- 插件目录下的 `skills/` 是**约定式自动加载**的，`plugin.json` 里写不写 `skills` 字段都会被扫到。

也就是说：**官方早就把"点一下装完"做好了，我却在自己造一套绕过 UI 的安装链。**

为什么会犯这个错：我当时只问了"文件该放哪"，没问"界面能做什么"。
找到了 `marketplace.json` 和缓存目录，就顺着文件系统往下推，做出了一个技术上成立、
但用户要敲命令的方案。**这是从实现倒推产品，不是从使用倒推实现。**

### 结论：v0.3.0 的三个改动

| 改动 | v0.2.0（作废） | v0.3.0 |
|---|---|---|
| 技能位置 | 包内 `skill_src/`，靠 `install.py` 铺到工作仓库再软链 | 包内 `skills/`，`plugin.json` 声明，导入专家时一起加载 |
| 数据目录 | 必须有工作仓库，脚本按层级找根 | 各技能 `_env.py` 自己找：环境变量 → 往上找工作台 → 默认 `文档/短剧工作区`（自动建） |
| ffmpeg | 让用户自己 `brew install` / `winget install` | Windows 版打进包内 `bin/`（ffmpeg.exe 61MB + ffprobe.exe 39MB） |

关键在第二行。之前不敢让技能自带，是因为 13 处 `parents[3]` 会指错地方；
而改这 13 处、又要保证本机 12 条片子照常跑，被判断为"风险不值"。
**这个判断本身就错了**——把风险当理由，最后把风险转嫁给了用户（让他敲命令、建仓库）。

真正做下来：新增一个 100 行的 `_env.py`，复制 6 份进各技能；13 处推导换成 `_data_root()`；
ffmpeg 定位前面加一层"先看包内 bin/"。半天工作量。

改完验证：本机 12 条片子状态照旧，装配器空跑 36 个刀口 0 问题；
干净环境（`HOME` 指到临时目录、cwd 在空目录）首次运行自动建好目录和配置，
只报「原片目录没填」和「出片密钥没填」两项——这两项本来就该人填。

包从 659KB 涨到 37MB（压缩后），换来的是用户全程不用碰命令行。

### 方法论：两条

1. **先找官方的路，再考虑自己造。** 造之前至少要能说出"官方为什么不行"。
   这次说不出来，就说明没查够。
2. **"能跑通"和"能给人用"是两个验收标准。** v0.2.0 在我这里是能跑通的，
   在非技术用户那里第一步就卡住。判断标准应该是"最不擅长电脑的那个人能不能独立完成"，
   不是"我照着 README 能不能做完"。

### 遗留的不确定

包内 `skills/` 会不会在导入后**确实**被 WorkBuddy 自动加载——本机没法验证，
因为这台机器上已经有同名的用户级技能，装了也会混在一起。
代码证据（插件技能 `source: plugin`、内置插件都是 `<插件>/skills/` 结构）指向"会加载"，
但没有真机证据。所以包里放了 `install.bat` 作为兜底：万一没加载，双击一次补上。
**这一条要在第二台机器上实测后回来改掉。**

## 九、「安装按钮不存在」——第二次从代码反推产品（2026-11-15 21:50）

张老师问：「WorkBuddy 没有官方的安装本地专家机制吗？我的专家没看到安装按钮。」

### 上一版错在哪

我把 `app.asar` 里 grep 到的 `importExpert`、`exportZip`、`installFromPath`、`importFromUrl`
这些**标识符**，当成了"界面上有导入按钮"。这一轮实测：在本机主程序里 grep
中文「专家」相关短语（导入专家 / 创建专家 / 专家市场 / 我的专家 / 上传技能……）
**命中 0 条**。说明中文界面文案不在主 bundle 里，从代码根本推不出界面有什么。

**同一个错误犯了两次**（第一次是"该放哪个目录"、这次是"界面有什么按钮"）。
共同点：手上只有代码，缺了产品那一半，就自己补了一段想象。

### 安装真正是什么

查 `expert-manager` 技能的 `register_expert.py` 与本机实际文件，安装＝登记三个地方：

| 落点 | 作用 | 缺了会怎样 |
|---|---|---|
| `…\.workbuddy\plugins\marketplaces\my-experts\plugins\<专家名>\` | 专家本体 | 完全没有这个专家 |
| 同级 `.codebuddy-plugin\marketplace.json` 的 `plugins[]` | 让 WorkBuddy 扫到 | 扫不到 |
| `…\.workbuddy\experts\custom\<用户ID>\experts.json` | 「我的专家」列表 | 不显示在列表，但已被扫到 |

本机第 3 份内容就一行：`["short-drama-trailer-editor"]`。它解释了为什么只放文件夹不登记会"装了看不见"。

### 改了什么

- 新增 `_setup.py`：跨平台，完成上述三步 + 把 8 个技能摆到用户级目录做兜底。
  **本机完整验证过**：解 zip → 跑 → 三个落点全对（含隐藏 `.codebuddy-plugin`）、
  `marketplace.json` 结构与本机一致、技能自检 8 项通过。
- 新增 `install.bat` + `_setup.ps1`：给没装 Python 的 Windows 用户，双击即可。
  旧的 `install.bat` 只铺技能，不装专家，已废止。
- `install.command` 改成调 `_setup.py`。
- `INSTALL.md` 重写：不再让人找按钮，改成"让那台电脑的 WorkBuddy 自己装"或"双击 install.bat"。

### 踩到的坑（写下来免得再踩）

1. `marketplace.json` 的 `source` 原本用**解压后的文件夹名**，文件夹一旦被改名就指向不存在的路径。
   改成固定 `./plugins/<专家名>`——落盘目录也用专家名，两边始终一致。
2. `_setup.ps1` 里有中文提示，PowerShell 5.1 读**无 BOM 的 UTF-8** 会按 GBK 解析成乱码，
   必须存成 UTF-8 **with BOM**。
3. `install.bat` 里全用英文输出、**不动 `chcp`**：默认代码页 936 反而才处理得了中文用户名路径。

### 仍未验证

本机没有 PowerShell，`_setup.ps1` 与 `install.bat` **没在任何 Windows 上真跑过**，
只做了逻辑等价实现 + Python 版等价验证。这一条要等第二台机器实测。

## 十、v0.3.1：资产库清场 + 团队共享规则（2026-11-16 08:3x）

张老师提了三件事：资产里还是商品内容、主管要记住分析完同步资产、专家包应该放资产里。

### 10.1 资产库从「电商」切成「短剧」

删了 6 项商品线内容（明细见 `docs/进度台账.md` 11-16 条目）。
删之前核过硬证据：根目录散落的两个 mp3 与本地 `assets/ai_assets/characters/ch_001_林岚/`
字节数完全一致，确认是副本，本机两份都在——**删网盘不丢东西**，所以敢动手。

保留 `过程文档/`：那是他自己的存档制度（技术决策存档 + 教学素材），
里面记着错误判断和翻案过程，删了写不回来。他认同保留。

### 10.2 人格文件新增「项目资产同步」一节

不只是加一句话，而是把「做完什么 → 传到哪里 → 什么状态下才传」列成表：

| 做完什么 | 传哪里 | 什么状态才传 |
|---|---|---|
| 剧集包 | `剧集包/<剧名>/` | G0 人审过了 |
| 素材索引 | `素材索引/<剧名>/` | 索引跑完自检过 |
| 定版成片 | `成片归档/<剧名>/<任务>/` | G3 人审过了 |
| 专家包新版本 | `专家包/` | 打包验证过 |

同时明确**不传**：原片 mp4（体积 + 版权）、中间产物、`.env` 和密钥（永不外传）、半成品。
并写死一条约束：**项目资产的写操作必须先给清单经人点头**——它不是本机文件，删错别人也受影响。

### 10.3 专家包放进资产：能做和不能做的边界

能做的：省掉「线下发文件」这一步，别人加入项目直接下载，版本管理靠文件名。
**不能做的**：网盘里的 zip 点一下就装好。WorkBuddy 没有从网盘链接一键安装的入口
（这条在第九节已经用实测否掉过一次，别再回头想）。

所以资产里放的是「包 + 安装说明」，下载后仍然是拖进对话或双击安装脚本。

### 10.4 一个操作事故，写下来

传 zip 时手抄安全令牌，中间多打了一个空格，服务端返回 `InvalidAccessKeyId`，
但 `curl` 退出码仍是 0，输出还打印了「上传完成」——差一点把失败当成功报出去。
**教训：这类上传命令必须加 `--fail`，并核对服务端响应**，不能只看 exit code。

## 十一、v0.4.0（2026-11-16）：无人值守 + 打包方式翻案

### 11.1 这一版加了什么

张老师要的是「从建档开始，一路跑到出片，最后给一份汇总报告」。做完发现内核不是
「写一个能从头跑到尾的程序」，因为八个环节里只有三个有真脚本，其余全靠模型判断后写文件。
所以「无人值守」的实际含义是：**判断由模型按预设规则自己做，做完留痕，最后一次性报。**

配套改了四件事：
1. `autopilot.py`（新，13 个阶段，status/run/report 三子命令）。三条设计规矩：
   每步幂等（产物齐就跳过，绝不重跑烧钱）／失败记日志继续／需要人拍板只喊「该你了」不自作结论。
   硬门槛只有 `{check, lines, tag}` 三步——它们挂了必须停，因为后面全靠它们喂数据。
2. 进度网页：不另起一套，在原有分镜台（`ui/server.py` + `index.html`）上加一个 tab
   和 `/api/autopilot` 接口。四个看点：跑到第几步／此刻在干什么／**半夜有没有死**／报告在哪。
3. 打包脚本 `pack_expert.py`（新）。
4. `check_env.py` 技能数从 7 改成 8——原来那 7 个不含主管自己，
   对外说「8 个技能」，自检却说「7 个齐全」，口径对不上。

### 11.2 打包方式翻案：macOS 的 zip 命令不能用

**症状**：包里带中文名的文件（`清单人审表_模板.md`、`状态模板_短剧.json`），
解压到 Windows 上文件名变乱码，技能调用这两个模板时找不到。从 v0.3.0 起就存在。

**原因**：文件名非 ASCII 时，标准做法是把 zip 的通用标志位第 11 位（0x800）标上，
表示「这个文件名是 UTF-8」。macOS 的 `zip` 命令不标，Windows 就按本地编码猜，于是乱码。

**改法**：用 Python `zipfile` 打包（它写非 ASCII 文件名时自动标这一位）。
`pack_expert.py` 打完会自检三件事：垃圾文件有没有混进去、中文名标没标对、包内版本号和目录名对不对。
实测：71 个文件、中文名 3 个全部标注正确、解压后文件名完整。

**顺带修的一处**：Mac 上双击用的 `install.command` 必须保留可执行位，
打包时按源文件权限写进 `external_attr`。用 Python 自带的 `extractall` 解压看不出这一点
（它不恢复权限），要用系统 `unzip` 或解压工具验证——**这条差点被误判成 bug**。

`deps.py`（新增，放主管技能 scripts 下，单点维护不进各技能副本）：

发行包同时装会互相覆盖 `cv2`，是已知坑，写清单前专门查了依赖树才避开。

### 13.6 补记：A4 是最该先改的一条（14:5x，测试机第二版报告）

第一版报告发过来时没有这一条，第二版补上了，**而且它是整份清单里最危险的一条**。

`progress.py` 的 `read_all()` 里探活写的是 `os.kill(pid, 0)`——POSIX 上的标准写法，
**在 Windows 上不是探活**：

CPython 的 `os.kill` 在 Windows 上只有两个信号走「发控制台事件」这条路，
其余一律 `TerminateProcess`。而 `signal.CTRL_C_EVENT` 的值**正好是 0**，
所以 `os.kill(pid, 0)` 实际执行的是 `GenerateConsoleCtrlEvent(0, pid)`，
也就是**向那个进程组发一次 Ctrl+C**。

后果两层，第二层才是要命的：

1. 探活必然失败——pid 不是控制台进程组组长时抛 `WinError 87`，被 `except` 吞掉，
   判定「进程不在」。于是网页上**每个在跑的任务都挂着红字「进程不在」**，
   而进程明明活着、产出还在长。
2. 万一那个 pid 恰好是组长，这一行**会真的把对方打断**。
   **一个自称「只读」的进度页，会在轮询时把正在跑的任务掐掉。**
   无人值守挂一晚上，可能半夜就是被自己的进度页送走的。

改法：新增 `progress.pid_alive()`。Windows 走 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`
+ `GetExitCodeProcess` 看退出码是不是 `STILL_ACTIVE`（259），全程只读；
POSIX 保持 `os.kill(pid, 0)`。`os.kill` 只在这一个函数里出现。

**踩坑细节**：`OpenProcess.restype` 必须写成 `wintypes.HANDLE`。
不写的话 64 位下句柄被截成 32 位，拿到的句柄直接无效——
探活会一直返回「进程不在」，看着跟没改一样。顺带把三个函数的 `argtypes` 也标上。

**顺手做了报告建议的第二件事**：把「进程死了」和「进程活着但没动静」拆开。
`read_all()` 多给一个 `health` 字段（`ok` / `dead` / `stalled`），
`alive` 和 `suspect` 保留（网页和下游都在读，删了连累别人）。
页面文案跟着分开：**「进程没了」→ 去翻日志找崩在哪；「没动静了」→ 进程还在，再等等或手动停**。
这两种情况的处置办法完全不同，混成一句「疑似中断」等于没给信息。

**验证**：本机 macOS 上两条分支都测了。POSIX 真跑（当前进程 True、999999 False）；
Windows 分支把 `ctypes` 整个换成假的、`os.name` 改成 `nt`，
三类结果（退出码 259 / 退出码 0 / OpenProcess 失败）3/3 对上。
网页接口 `/api/progress` 实测三种记录分别判成 ok / dead / stalled。

**没验证的**：Windows 真机没跑过这条新路径（本机是 Mac）。
逻辑自测过了，但要等测试机下一轮才算数。

## 十四、v0.4.2 续：ffmpeg 不再打进包（11-16 晚）

### 14.1 一句话结论

张老师问「不打包 ffmpeg、像依赖一样让它自己装，体积是不是更小」——
**体积上他说对了，而且是断崖式的**：

| | 大小 |
|---|---|
| 原来整包 | **37.2 MB** |
| 其中 `bin/` 两个 exe | **36.5 MB（98.1%）** |
| 去掉之后 | **0.72 MB**（实测打出来的包） |

但「像 Python 库一样指定版本让它装」这条路**不通**，理由见下。

### 14.2 实测：pip 上那个包缺一半

把 `imageio-ffmpeg 0.6.0` 两个平台的 wheel 都拉下来拆开看了：

| 平台 | 内容 | 带 ffprobe |
|---|---|---|
| macOS x86_64 | `ffmpeg-macos-x86_64-v7.1` 72.5 MB | **否** |
| Windows amd64 | `ffmpeg-win-x86_64-v7.1.exe` **83.6 MB** | **否** |

两个问题：

1. **只有 ffmpeg，没有 ffprobe。** 而「这一段最多能切到第几秒」是靠 ffprobe 读
   视频流时长算的（工程铁律），缺了它整条判断作废。
2. **它 Windows 版单文件 83.6MB，比原来包里那份 64MB 还大。** 换成它体积不减反增。

所以不是「没人做」，是**那个包不完整，而且更大**。

另有一个 `static-ffmpeg` 包证明了这个模式可行：包本体只有 **0.02 MB**，全是代码，
二进制运行时再下。但它的下载源同样走 GitHub，国内不稳。

### 14.3 定下来的方案（张老师选 B）

**包里不带可执行文件，按平台下，缓存在数据目录 `bin/`。**

| | 包大小 | 代价 |
|---|---|---|
| A 保持打包 | 37.2 MB | 每发一版都重下同一份 36.5 MB；Mac 用户白背 Windows 的 exe |
| **B 按平台下（采用）** | **0.72 MB** | 第一次要下 30–120 MB |

选 B 的真正理由不是省体积，是**顺带解决了两个原来的毛病**：

- **Mac 用户白背 36.5MB**：包里只有 Windows exe，Mac 上根本用不到，全靠系统里的 ffmpeg。
  要是那台 Mac 没装过 ffmpeg，这条链一步都跑不了。
- **每版升级重下同一份**：ffmpeg 是同一个文件，跟着专家包版本重复下载。
  放到数据目录后一部机器只下一次。

**必须如实说清的代价**：第一次开工（或手工安装的第 6 步）要下 30–120MB。
实测本机 macOS 走代理下 32.2MB×2，一次 3 分 45 秒，另一次 10 分钟以上——
**国内网络下这个时间不可控**。所以设计上做了三件事缓释：
前置到体检（第一步就下，不拖到装配）、失败冷却 24 小时、下不动时降级用旧版。

### 14.9 换源：慢不是错觉，是境外源的物理速度（11-16 22:30 补）

**怎么发现的**：改完当晚跑一次干净环境的完整下载验证，跑到 30.0 / 32.2 MB（93%）
用了 **20 分 05 秒**，被叫停。张老师问「半小时了，这么慢，检查一下」。
第一反应以为是卡死或代码有问题，量了一遍速度才发现——**程序没问题，是源慢**。

**实测四个源**（同一条千兆宽带，同一时间，只保温 12 秒取前 3–4 MB）：

| 源 | 实测速度 | 32MB 要多久 | 备注 |
|---|---|---|---|
| martin-riedl.de（mac/Linux 原用） | 25～150 KB/s | 20 分钟以上 | 三次实测波动大，最慢一次 25 KB/s |
| gyan.dev（Windows 原用） | **9 KB/s** | **114MB 要三个半小时** | 完全不可用 |
| ghfast.top（GitHub 代理） | 172 B/s | — | 返回 146 字节，等于不通 |
| **淘宝 npm 二进制镜像** | **700 KB/s～1.9 MB/s** | **Windows 两件 59MB：1 分钟** | 走国内线路 |

**换成什么**：`registry.npmmirror.com/-/binary/ffmpeg-static/b6.1.1/`。
它镜像的是 npm 包 `ffmpeg-static` 的官方发布件（macOS 是 evermeet 的 tessus 构建，
Windows 是 gpl 构建），**每个程序一个 `.gz`，解开就是可执行文件**——
不用解 zip 找路径，少一层出错机会。

| 平台 | ffmpeg + ffprobe 两件 | 实测耗时 |
|---|---|---|
| Windows x64 | 28.2 + 28.2 = 56.4 MB | 约 1 分钟（两路并行） |
| macOS arm64 | 18.4 + 18.3 = 36.7 MB | 约 40 秒 |
| macOS x64 | 24.1 + 24.1 = 48.2 MB | **30 秒**（实测，7 核空闲） |
| Linux x64 / arm64 | 28.0 + 27.9 / 24.4 + 24.3 | 同量级 |

**三个跟着改的点**：

1. **两路并行下**。单路约 700 KB/s，两条独立连接能跑到 1 MB/s 出头，
   Windows 那 59MB 从两分钟压到一分钟。`_fetch_gz()` 用两个线程，各带标签报进度。
2. **版本门槛 7 → 6**。原来卡 7.x，导致本机明明有 6.1 也要重下——**这是当晚白等
   20 分钟的一半原因**。6.x（2023 年起）对我们的需求完全够，只有 `<6` 或压根没有才下。
   `MIN_MAJOR = 6`。
3. **境外源降级成备源**。gyan / martin-riedl 的代码路径保留，排在主源后面，
   只在主源整段不通时兜底。`_hint()` 里的「手动补」也改成给国内镜像地址。

**6.1.1 够不够用（担心降版本，实测过）**：
`ffmpeg version 6.1.1-tessus`，实测带 `libx264` / `libx264rgb` / `libx265` / `aac` /
`loudnorm` / `alimiter` / `blackframe` / `select`；真跑了一遍装配管线——
concat 蒙太奇、`loudnorm+alimiter` 接 `libx264` 加 `+faststart`、`setsar`/`scale`、
`-stream_loop`、lavfi 造黑场、`-ss -to -c copy` 精确切段，**六项全过**。
顺手验了那条工程铁律：同一条片子 `ffprobe` 读 video stream duration 3.08s、
format duration 3.10s，差 0.02s——**出点必须按流时长算，这条依然成立**。

想要 8.x 也行：同一个镜像里有 `ffmpeg-builds/v8.1.3/ffmpeg-8.1.3-win32-x64-gpl.tar.xz`，
134MB，带 libx264，下两三分钟。**但 6.1.1 体积只有它四成、速度快一倍，功能一样够**，
所以默认 6.1.1；真要升就改 `_NPM` 那一行 + 走 `ffmpeg-builds` 的 tar 分支。

**为什么不用 `ffmpeg-builds` 通吃**：它只有 Windows 和 Linux 的构建，没有 macOS，
mac 还得另找源；而 `ffmpeg-static` 五个平台都齐，一套代码走完，不必为平台分支写特例。

**顺带清掉一处测试残留**：仓库根下有个未入库的 `bin/`，是当晚测 9.0.2 时下下来的
（ffmpeg + ffprobe 共 190MB）。它挡在 `_env.tool()` 的第一顺位，导致带缓存目录跑
也报「9.0」——查了才发现是它。已移到 `/tmp/repo_bin_testjunk_20261116`，没删。
